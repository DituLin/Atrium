# Atrium 产品迭代开发计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 在已验证的 Mac mini / NAS / OnePlus TV 和 AI 接入基础上，交付宋式照片体验，再逐步接入家庭今日概览、房屋信息、日历与视频。

**Architecture:** 延续 Go Core、只读 NAS、React TV 页面和 Android WebView 容器。AI Brain 保持独立，家庭概览由确定性数据汇总；新增数据源、媒体类型和页面先明确契约，再接入真实内容。

**Tech Stack:** 现有 Go / SQLite / HTTPS / WebSocket、React / TypeScript / Vite、Android Java / WebView、OpenClaw / home-mcp；不在本计划中预先增加新运行时。

用户确认“做个普通日历就可以”，本轮改为本地公历月历、今天标记、前后月及回到本月、家庭时区与全遥控操作。外部共享日历、事件解析/同步、日程公开字段移出本轮必要交付，不再等待来源确认；下文 C1–C3 及原 M3 真实日历门槛作为历史方案保留。新实施与验收见 [普通月历设计](2026-09-13-basic-calendar-design.md)。真实家庭提示内容与房屋资料仍按实际提供情况显示；不伪造传感器或日程。

## 1. 基线与范围

- 制定计划时，AI 与重复图片确认修复位于 `.worktrees/ai-brain-mcp`，主工作区含 Android / NAS 未提交改动。T01 已将两组改动保全并集成至 `codex/product-iteration`，构建部署和三端/AI 回归通过；原工作区继续保留，不等于已经合并回主分支。
- 制定计划时只有基础照片功能与宋式讨论稿；执行后已交付 M2 宋式照片候选版，后续模块仍不能按设计稿认定完成。
- 第一轮目标是“宋式照片版”；后续增加家庭概览与视频。原 PRD 的正式 V1 验收仍是独立门槛。
- Mac 断电恢复、NAS 自动挂载继续暂停。房屋设备控制、长期记忆、语音、多 Agent、全量实时视频转码不随此次迭代自动加入。
- 原有方案中的“AI 尚未交付”是历史记录，以 9 月 7 日 AI 验收结果为准。本文替代旧产品路线的执行顺序，不改写历史测试结果。

## 2. 路线选择

采用“照片体验优先，数据模块逐项接入”。它能让下一次交付直接改善现有设备上的日常使用，也能在尚未确定日历和传感器来源时持续推进。

其他路线暂不采用：一次铺开所有页面会被数据源和视频兼容性牵制；先扩展 AI 工具对当前 TV 视觉与遥控体验改善有限。已有 AI 能力随页面改动持续回归。

## 7. 检查与发布规则

在集成工作区根目录执行：

```sh
make check
node --test adapters/openclaw/*.test.mjs
npm --prefix web run lint
npm --prefix web test
npm --prefix web run build
```

预期均退出 0，lint 无问题。首次集成执行全仓 race；后续依据改动运行相关包 race。前端资源需要按 `make web-sync build` 嵌入 Core，再按已记录的备份/替换流程部署；不把只更新 web/dist 当成设备已更新。

仅原生代码变化时，在 `android-tv/` 按 README 配置 SDK/JDK 后执行：

```sh
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug \
  -PatriumCa=/Users/ditu/Atrium/data/tls/ca.crt
```

实机脚本使用显式的测试屏幕、配置及二进制路径；需操作网络时只针对指定测试机并保证恢复。每个任务完成对应检查后提交，按阶段审查，不以提交数量或测试数量当作产品完成率。

M5 沿用 `docs/ops/acceptance.md`：API/首屏/控制延迟、100 次变更推送、100 张 × 5 批新增、至少 10 次重连、NAS 恢复、缓存与资源预算、24 小时展示、7 天可用性、备份恢复及安全矩阵。正常网络基线与故障场景分别记录；模型等待单独计时。

Mac 断电恢复、NAS 自动挂载不得自动恢复排期。暂停项如果使某条正式发布条件无法满足，就保留“家庭测试版/有运行条件的候选版”标识，不将门槛删掉或勾选通过。
